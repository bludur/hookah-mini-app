# Hookah Mini App

Telegram Mini App и бот для коллекции табаков и подбора миксов. API: FastAPI; бот: aiogram; интерфейс: React/TypeScript. Общий пакет `hookah_core` содержит модели, проверки данных, генерацию и ограничения расхода LLM.

## Локальная установка

Нужны Python 3.11 и Node 24 (проверенная версия 24.13.0, npm 11.6.2). Для production используйте Python 3.11.16 или более новый security patch ветки 3.11. Все Python-команды выполняются **из корня репозитория**. Бот и API используют один набор зависимостей.

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
Copy-Item .env.example .env
```

В `.env` заполните `BOT_TOKEN` и `LLM_API_KEY`, проверьте `LLM_API_URL` и `LLM_MODEL`. Секреты не добавляются в Git. По умолчанию используется один SQLite-файл `hookah_app.db` в корне для обоих приложений.

```powershell
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn --app-dir mini-app-backend main:app --host 127.0.0.1 --port 8000
```

В отдельном терминале для бота:

```powershell
.\.venv\Scripts\python.exe -m bot.main
```

Для интерфейса:

```powershell
cd mini-app-frontend
npm ci --ignore-scripts
npm run dev
```

На Linux/macOS вместо `.venv\Scripts\python.exe` используйте `.venv/bin/python`.

Авторизация обязательна и при разработке: откройте интерфейс из Telegram через HTTPS-адрес разработки и включите его origin в `CORS_ORIGINS`. При открытии в обычном браузере приложение показывает инструкцию входа; общего тестового пользователя и обхода подписи нет. Для автоматических тестов используются отдельные тестовые ключи и базы.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m pip check
cd mini-app-frontend
npm test
npm run build
npm audit --audit-level=high
```

Тесты проверяют подпись, возраст и структуру Telegram initData, изоляцию пользователей, дубликаты и гонки создания, миграции старой БД, допустимость ответов AI, квоты и ошибки интерфейса. Redis Lua проверяется локально через fakeredis. При заданных `TEST_POSTGRES_URL` и `TEST_REDIS_URL` включаются интеграционные проверки; используйте **только отдельные тестовые сервисы**. GitHub Actions поднимает PostgreSQL и Redis для этих проверок.

## Правила безопасности и данных

- API принимает только `X-Telegram-Init-Data`. HMAC проверяется на сервере, данные старше `TELEGRAM_AUTH_MAX_AGE` (по умолчанию 1 час) отклоняются. Имя на экране не участвует в авторизации. Алгоритм: [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).
- Бот обслуживает только личные чаты. Запросы отдельных объектов и массовое удаление ограничены владельцем.
- Один пользователь: не более 10 генераций в час и 30 в сутки; общий бюджет — 1000 попыток в сутки; одновременно — 4 генерации на приложение и 1 на пользователя. Все значения настраиваются. Неуспешные попытки тоже расходуют квоту; автоматических повторов платного запроса нет.
- Production использует общий Redis для бота и API. При его недоступности новые генерации запрещены. Redis должен сохранять данные и использовать `noeviction`, иначе потеря счётчиков сбросит квоты. Локальные счётчики предназначены только для одного процесса разработки.
- Допускаются 2–4 уникальных компонента из коллекции с положительными целыми долями в сумме 100%. Выбранная база должна присутствовать в роли базы. Ошибочный ответ провайдера не записывается в БД.
- Запрос API ограничен 64 KiB, массовое добавление — 100 строками, коллекция — 200 табаками. Имена нормализуются Unicode NFKC + casefold для проверки уникальности внутри коллекции.
- В обновлениях отсутствующее поле сохраняется; явный `null` очищает бренд, категорию или заметки. Название обнулить нельзя.
- Ошибки SQL и провайдера не возвращаются пользователю и не записываются целиком в журнал. Логируются тип ошибки и событие; токены и initData не следует включать в access-логи прокси.
- Схема меняется только через Alembic. Startup проверяет версию; `create_all` в приложении больше не используется.
