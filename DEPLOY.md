# Развёртывание и переход с прежней версии

## Обязательные действия перед обновлением

В старой версии DEPLOY.md находился ключ OpenRouter. Его значение удалено из текущего файла, но **отзыв ключа у провайдера обязателен**: удаление строки не аннулирует ключ, старые Git-коммиты и копии сохраняют его. Отзовите старый ключ в панели OpenRouter, создайте новый с подходящим лимитом расходов и замените `LLM_API_KEY` у бота и API. Проверьте расходы провайдера. Эти операции не выполняются изменением исходников.

После ротации при необходимости согласуйте очистку истории через git-filter-repo и обновление клонов. Не делайте force-push без согласования с участниками проекта. Переписывание истории не заменяет отзыв ключа.

## Данные и миграции

1. Остановите запись в прежнюю БД: старые версии бота и API несовместимы с новым обязательным `normalized_name`.
2. Сделайте резервную копию и проверьте восстановление на отдельной базе.
3. Явно задайте `DATABASE_URL` существующей БД. Раньше бот по умолчанию писал в `hookah_bot.db`, API — в `hookah_app.db`. Обновление не объединяет эти файлы автоматически. Выберите источник данных либо подготовьте отдельный импорт с разрешением конфликтов.
4. Выполните из корня: `python -m alembic upgrade head`.
5. Запустите API и бот на одной БД, с одинаковыми `BOT_TOKEN`, `REDIS_URL` и `APP_ENV`.
6. Обновите frontend одновременно с API: старые заголовки `X-Telegram-User-Id` больше не принимаются.

Миграция принимает полную старую схему без Alembic, добавляет нормализованное имя, уникальное ограничение, индексы и проверку рейтинга. Она останавливается при дубликатах, некорректных ссылках и рейтингах, сообщая идентификаторы записей. Она не удаляет и не сливает пользовательские записи. Исправьте конфликт в копии БД и повторите проверку, затем примените согласованное исправление к рабочей базе.

Старые рецепты сохраняются как исторические данные. Проверка новых ответов AI не исправляет старые некорректные рецепты задним числом.

Для отката предпочтительно восстановление проверенной копии с согласованной версией кода. Снижение миграции до пустой схемы запрещено, поскольку удалило бы пользовательские данные.

## Production

Настройки обязательны:

| Переменная | Значение |
|---|---|
| APP_ENV | production |
| BOT_TOKEN | токен того бота, который открывает Mini App |
| LLM_API_KEY | новый ключ провайдера |
| LLM_API_URL | HTTPS endpoint провайдера |
| LLM_MODEL | доступная вашему аккаунту модель |
| DATABASE_URL | постоянная PostgreSQL-база; обычные postgres:// и postgresql:// преобразуются в asyncpg |
| REDIS_URL | общий Redis бота и API, с persistence и noeviction |
| CORS_ORIGINS | точные HTTPS origins frontend, через запятую, без пути и завершающего / |

Приложение не запускается в production с SQLite, пустыми ключами, отсутствующим Redis или wildcard CORS. CORS не заменяет авторизацию. Ограничьте доступ к PostgreSQL и Redis приватной сетью; для внешних соединений настройте TLS. Вынесите TLS, ограничения подключений и таймауты медленных запросов на входной reverse proxy. Общий лимит расходов у LLM-провайдера служит дополнительным ограничением бюджета.

Секреты задавайте через настройки окружения платформы. Используйте отдельные аккаунты и ключи для разработки и production. Подключайте журналы и оповещения на рост 401/429/5xx, ошибки Redis и расходы LLM.

## Render

По требованию бесплатного размещения **render.yaml в корне репозитория** теперь описывает только API на Render Free. PostgreSQL подключается из Neon Free, Redis — из Upstash Free. Платные ресурсы Render не создаются. Подробные параметры и ограничения — в [FREE_DEPLOY.md](FREE_DEPLOY.md). Сам файл не означает, что ресурсы созданы или существующий сервис обновлён.

Root Directory Python-сервисов — корень, потому что они импортируют `hookah_core`. У Free нет `preDeployCommand`: выполните миграции отдельной командой с компьютера с доступом к PostgreSQL, затем запустите ручное развёртывание. Автоматическое развёртывание отключено в профиле. Проверка Render использует `/healthz` без запросов к БД; `/api/health` остаётся проверкой соединения с БД. [Поля Blueprint](https://render.com/docs/blueprint-spec).

Frontend разместите как Static Site:

- Root Directory: `mini-app-frontend`.
- Build: `npm ci --ignore-scripts && npm run build`.
- Publish Directory: `dist`.
- `VITE_API_URL`: HTTPS URL API с окончанием `/api`.
- Node: версия из `.node-version`; npm 11.6.2.

Добавьте origin frontend в `CORS_ORIGINS`, затем укажите URL Mini App в BotFather. Для бота создайте worker с командой `python -m bot.main`, установите тот же набор переменных и БД. Запускайте один polling-процесс для одного BOT_TOKEN. Worker запускается после успешных миграций API.

SQLite на временном диске Render не обеспечивает сохранность: [persistent disks](https://render.com/docs/disks). Production-конфигурация поэтому требует PostgreSQL.

## Резервные копии

Настройте регулярные резервные копии PostgreSQL средствами платформы или `pg_dump`. Храните их с ограниченным доступом отдельно от основного сервиса, задайте срок хранения и периодически восстанавливайте копию в отдельную БД. Для локального SQLite используйте его backup API или копирование при остановленных процессах, а не копирование открытого файла во время записи.

Перед выпуском проверьте: `/api/health`, вход настоящего пользователя из Telegram, невозможность доступа второго пользователя к его данным, генерацию с отдельным тестовым ключом, ротацию секрета и восстановление резервной копии.
